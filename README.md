# FraudShield

**Real-time fraud detection service**: point-in-time-correct features, a calibrated LightGBM model with a cost-aware approve/review/block policy, streaming feature updates (Redpanda + Quix Streams + Redis), a champion/challenger MLOps loop (MLflow + Prefect), drift monitoring (Evidently, Prometheus, Grafana) and an analyst review UI (React).

> **Status: under construction (Phases 0-6 coded: foundations, point-in-time features, modeling, scoring API, streaming, MLOps loop, monitoring).** See [PLAN.md](PLAN.md) for the roadmap. No model metrics are reported yet. Every number that appears here later will be produced by a script in this repo that you can rerun.

## Quickstart (development)

Requirements: [uv](https://docs.astral.sh/uv/) ≥ 0.12.23, GNU make, git. Python 3.12 is installed by uv if missing.
On macOS, LightGBM also needs the OpenMP runtime (`brew install libomp`); alternatively, `make test-docker` runs lint and tests in a Linux container with only Docker installed.

```bash
make setup   # install locked dependencies + pre-commit hooks
make lint    # ruff + mypy (strict)
make test    # unit tests
make help    # all targets (later-phase targets report "not implemented yet")
```

## Data and features

| Dataset | Source | Access | Entity (`uid`) |
|---|---|---|---|
| IEEE-CIS (primary) | Kaggle competition `ieee-fraud-detection` | Kaggle token + accepted [rules](https://www.kaggle.com/competitions/ieee-fraud-detection/rules) | `card1_addr1_D1n` |
| Sparkov | Kaggle dataset `kartik2112/fraud-detection` (CC0) | public, no credentials | `cc_num` |

```bash
make data DATASET=sparkov            # download + verify against data/manifests/sparkov.raw.json
make features DATASET=sparkov        # canonical + point-in-time feature parquet
make features-check DATASET=sparkov  # rebuild and verify content hashes against the committed manifest
make eda DATASET=sparkov             # run notebooks/01_eda.ipynb
```

For IEEE-CIS, set `KAGGLE_API_TOKEN` (or create `~/.kaggle/kaggle.json`) first, then run the same targets with `DATASET=ieee_cis`. Feature semantics, including windows, label delay and target encoding, are documented in [`features/definitions.py`](src/fraudshield/features/definitions.py) and ADRs 0004–0006.

## Modeling

```bash
make tune DATASET=ieee_cis    # Optuna, rolling-origin CV inside train -> configs/tuned/ieee_cis.json
make train DATASET=ieee_cis   # rules-only, logistic, LightGBM degraded + full; calibrate; evaluate on test;
                              # log to MLflow (SQLite locally) and register models:/fraudshield@challenger
make docs DATASET=ieee_cis    # docs/model_card.md from reports/ieee_cis/metrics.json
```

Decisions use expected costs from [`configs/costs.yaml`](configs/costs.yaml) with a daily review capacity. The hard rules in [`configs/rules.yaml`](configs/rules.yaml) are both the rules-only baseline and the serving pre-check. See [ADR-0008](docs/adr/0008-modeling-policy-and-packaging.md). Results will appear here once the real-data training run has been done; none have been produced yet.

## Scoring API

```bash
docker build -t fraudshield-api .
docker run -p 8000:8000 -v $PWD/artifacts:/app/artifacts:ro fraudshield-api   # serves artifacts/ieee_cis/bundle
curl -s localhost:8000/ready
curl -s -X POST localhost:8000/score -H 'content-type: application/json' \
  -d '{"txn_id": "t1", "uid": "13926_315_-13", "amount": 68.5, "product": "W", "extra": {"C1": 1}}'
```

`POST /score` returns `probability`, `decision` (approve / review / block), up to three `reason_codes`, `model_version`, `degraded` and `latency_ms`. If the feature store is slow or down, the service falls back to a request-only model, and if the model fails it falls back to the hard rules. Internal faults never produce a 5xx (see [ADR-0009](docs/adr/0009-serving-design.md)). Other endpoints: `/health`, `/ready`, `/metrics` (Prometheus), `/events/stream` (SSE), `/cases` (review queue), `/model`, `POST /admin/reload`.

In-process latency on a synthetic bundle of production-like size: [reports/benchmarks/serving_inprocess.md](reports/benchmarks/serving_inprocess.md), generated by `make bench-docker`.

## Streaming stack

```bash
make up                                        # Redpanda, Redis, API, processor, gateway, label emitter, parquet sink, shadow
make replay RATE=50 ARGS="--max-events 300"    # replay the committed CC0 fixture through Kafka
make test-integration                          # end-to-end checks on the running stack
make down
```

Topology: replayer → `transactions.raw` → gateway → `POST /score` → `decisions` → processor (keeps the Redis feature store current), Parquet sink, shadow scorer (`@challenger` → `shadow.scores`). Ground-truth labels are released to `labels` once their simulated availability time is reached. Redpanda Console runs on http://localhost:8080. Each worker exposes `consumer_lag_seconds` on its metrics port (9101-9105). Until the real training run the stack serves dev models trained on the fixture (`make dev-bundle`); see [ADR-0010](docs/adr/0010-streaming-design.md).

## MLOps loop

```bash
make mlops-demo          # one command, synthetic data: retrain -> @challenger -> gate + shadow -> promote -> rollback
make up-mlops            # + Postgres, MLflow server (http://localhost:5050), Prefect (http://localhost:4200)
make retrain promote DATASET=ieee_cis   # real data (after `make features`)
make rollback            # @champion back to the previous version; the API hot-reloads
fraudshield canary 10    # send 10 % of cards to @challenger
```

Promotion moves the MLflow alias `@champion` only if the challenger passes every check: PR-AUC within 0.005 of the champion, net savings at least the champion's, single-row p95 latency ≤ 5 ms, and online/offline feature parity. A shadow comparison is reported alongside. Retraining uses matured chargeback labels plus analyst labels, point-in-time (see [ADR-0011](docs/adr/0011-mlops-loop.md)). Prefect runs `retrain-and-promote` weekly.

## Monitoring and drift

```bash
make up-all       # + Prometheus (http://localhost:9090) and Grafana (http://localhost:3000, anonymous viewer)
make drift-demo   # normal replay, then a 40 % "fraud ring" -> drift job -> DriftDetected alert -> retrain
```

A daily Prefect job compares the served features (from the decision log) against the previous week. It checks Evidently feature drift on the champion's top-20 features, score PSI, the decision mix, and PR-AUC on matured labels, and triggers retraining when any threshold is crossed. Grafana dashboards: Service SLOs, Decision & Score mix, Champion vs Challenger, Pipeline health. Alerts cover p95 latency, fallback rate, consumer lag, drift and down targets. The latest demo run is summarised in [reports/drift/demo-summary.md](reports/drift/demo-summary.md); see [ADR-0012](docs/adr/0012-monitoring-and-drift.md).

## Analyst UI

```bash
make up-ui        # core + mlops + ui: the UI on http://localhost:5180, review cases stored in Postgres
make replay RATE=50 ARGS="--max-events 300"
make ui-dev       # or: Vite dev server on http://localhost:5173 against `make up` (Node 24)
make ui-test      # typecheck + vitest
```

Five pages:
- **Live feed**: decisions over SSE, with a throughput sparkline.
- **Review queue**: ordered by expected loss. Keyboard: `F` fraud, `L` legit, `E` open the case, `J`/`K` move.
- **Case detail**: transaction fields, the three reason codes (value vs typical), the card's last 20 events, other cards on the same device or email domain, label buttons with notes, and the audit trail.
- **Model & monitoring**: champion/challenger versions, decision mix, latency, and the latest drift check with its Evidently report.
- **Policy simulator**: change the cost assumptions and the daily review capacity, and see decisions and net savings recomputed on the champion's held-out window.

A label is written to Postgres (`cases`, `labels`, `audit_log`) in one transaction, and published to the `labels` topic. The next `build-training-set` run picks it up, which is tested end to end. nginx serves the build and proxies `/api` to the service; admin endpoints are not exposed there. See [ADR-0013](docs/adr/0013-analyst-ui-and-case-store.md).

## Load test

```bash
make loadtest     # stack with a production-sized synthetic model; Locust: normal / no reason codes / Redis killed
```

Locust sends Poisson-distributed requests: 70 % from returning cards, 30 % from new ones. While it runs, the orchestrator samples the API's metrics and kills and restarts Redis for the third scenario. The generated report, [reports/loadtest/report.md](reports/loadtest/report.md), has:
- client and service latency;
- failed requests;
- the share of requests on a fallback path;
- charts.

The first runs found three problems: a circuit breaker that turned short stalls into 30 s of degraded scoring, distinct-count features that read a whole email domain's history on every request, and model inference blocking the event loop. All three were fixed, with tests ([ADR-0014](docs/adr/0014-hardening-and-deployment.md)).

## Demo and deployment

```bash
make demo         # ONE container: API + in-process replayer + in-memory stores + UI -> http://localhost:8088
make demo-check   # 3 minutes at 50 tx/s: UI and API up, memory under 1 GiB -> reports/demo/demo-check.md
make up-lite      # the full system trimmed for an 8 GB laptop (compose.lite.yml)
```

- On every push to `main`, CD builds multi-arch images (amd64 + arm64) for the API, trainer, demo, UI and MLflow, and pushes them to GHCR. An optional SSH deploy job can follow.
- A weekly workflow triggers retraining on the deployed Prefect server and checks the training pipeline on synthetic data.
