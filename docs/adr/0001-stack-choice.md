# ADR-0001: Technology stack

- Status: Accepted
- Date: 2026-10-23
- Phase: 0

## Context

FraudShield is a solo-built, production-style real-time fraud detection service. It must:

- run end to end on a 16 GB laptop, with an 8 GB "lite" profile, and offer a single-container demo under 1 GB RAM;
- run on arm64 (Apple Silicon for development, possibly an Arm VM for deployment), so every image needs an arm64 variant;
- be reproducible: pinned versions, data manifests, and metrics regenerated by scripts;
- use one feature definition with an offline and an online executor that are provably equal (the parity test).

## Decision

| Concern | Choice | Why |
|---|---|---|
| Language / env | Python 3.12, **uv** (lockfile) | Fast, deterministic installs; one tool for venv, lock and run. |
| Tabular data | **Polars** (primary), **DuckDB** (SQL/as-of joins), pandas (library interop only) | Polars/DuckDB are fast on a laptop and support time-ordered, point-in-time windowing. pandas is kept only where libraries (shap, evidently) need it. |
| Model | **LightGBM 4.7.x** | Fast CPU training and inference, native categorical handling, `pred_contrib=True` gives per-row SHAP contributions without extra dependencies, and `num_threads=1` gives predictable latency. |
| Tuning | Optuna | Time-aware CV via a custom objective. Imbalance is handled with `scale_pos_weight`, not SMOTE (resampling breaks calibration and temporal realism). |
| Explainability | booster `pred_contrib` (serving), shap 0.54.x (offline plots) | Native contributions keep the serving path light. |
| Tracking / registry | **MLflow 3.x**, registered-model **aliases** `@champion` / `@challenger` | Stages are deprecated; aliases are the supported promotion mechanism. |
| Orchestration | **Prefect 3.8.x** | Pure-Python flows, small footprint, and flows can run without a server (needed for the lite profile). |
| Drift | **Evidently 0.7.x** (new API: `Report`, `Dataset`, `DataDefinition`, `evidently.presets`) | Maintained; we write against 0.7 directly. Older tutorials do not apply. |
| Broker | **Redpanda v26.2.x** (`--smp 1 --memory 1G --overprovisioned`) + Console | Kafka API in a single binary with no ZooKeeper/KRaft cluster to manage, and an explicit memory cap. |
| Stream processing | **Quix Streams 3.x** | Maintained, pure Python, Kafka-native. Bytewax is rejected because its company no longer maintains it. |
| Online store | **Redis 8.x** behind a `FeatureStore` interface (Redis + in-memory implementations) | Pipelined reads give low latency; the in-memory implementation powers tests and the demo container. |
| Serving | FastAPI + uvicorn + orjson + pydantic v2 | Typed contracts, async, cheap JSON. |
| Cases DB | Postgres | Shared with the MLflow backend in the full profile. |
| Metrics / dashboards | prometheus-client, Prometheus, Grafana (provisioned) | Standard, arm64 images available. |
| Validation | pandera (dataframes), pydantic (records) | Schema checks at the adapter and feature boundaries. |
| Testing | pytest, hypothesis (PIT/no-leakage properties), httpx (API), locust 2.x (load) | |
| Quality | ruff (lint + format), mypy `--strict` | |
| UI | React + Vite + TypeScript + TanStack Query + Recharts, served by nginx | |
| Feature store framework | **Not used initially**. Feast is optional later, pinned exactly (pre-1.0). | Our own two-executor design is smaller and lets us test PIT correctness directly. |

Compose profiles: `core`, `mlops`, `monitoring` and `ui` in `compose.yml`; `compose.lite.yml` for 8 GB; `compose.demo.yml` for a single container. Every service gets a healthcheck and a memory limit.

## Alternatives considered

- **Apache Kafka (KRaft)** instead of Redpanda: heavier JVM footprint on a laptop; rejected.
- **Bytewax**: no longer maintained by its company; rejected.
- **Airflow / Dagster** instead of Prefect: heavier to run locally (Airflow), or more concepts than we need (Dagster).
- **XGBoost / CatBoost**: comparable accuracy. LightGBM wins on training speed and native `pred_contrib` at serving time.
- **Feast from day one**: adds a registry and a provider abstraction we don't need yet, and it is pre-1.0.

## Consequences

- Several fast-moving dependencies (MLflow, Prefect, Evidently, Quix Streams, Redpanda) each need a changelog check before pinning. See ADR-0002.
- The parity test (online vs offline executor) is the main guard against training/serving skew, because no feature-store framework enforces it for us.
- Revisit if the memory budget can't be met, or if a chosen component loses maintenance or arm64 support.
